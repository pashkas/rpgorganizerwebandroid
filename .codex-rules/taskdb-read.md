# Taskdb Read

Выполняй ограниченные read-only lookup rounds, чтобы получить применимый прошлый контекст для текущей проектной задачи.

## Decide

- Явная просьба пользователя поискать в taskdb всегда запускает lookup.
- Без явной просьбы запускай lookup один раз в начале новой нетривиальной рабочей задачи.
- При смене рабочей задачи считай её новой и выполняй отдельный lookup для её контекста.
- В ходе текущей задачи разрешён дополнительный targeted lookup, если новые сведения, обнаруженный риск, незнакомый контур или развилка решения показывают, что прошлого контекста недостаточно.
- Не повторяй уже выполненный lookup с тем же смыслом без новых поисковых терминов или явной просьбы пользователя.
- Не запускай автоматический lookup для простого вопроса, статуса текущей работы или объяснения уже найденного кода.
- Обычные уточнения в рамках той же задачи сами по себе не требуют повторного lookup.
- Начальный автоматический lookup заверши до чтения кода, поиска файлов, плана и правок; дополнительный выполняй сразу после появления обоснованной потребности в контексте. Не выполняй lookup параллельно с дальнейшей работой, зависящей от его результата.

## Project And Query

- Если известен один проект, используй его имя.
- Если задача затрагивает несколько известных проектов, один lookup round может содержать отдельный lookup для каждого контура.
- Если имя проекта отсутствует или конфликтует, скажи `taskdb не инициализирован или имя проекта неясно` и продолжай без lookup.
- Делай `query` коротким: домен, действие, classes, files, endpoint и точные errors.
- Сохраняй точные identifiers и добавляй распространённые варианты записи, только если они помогают поиску.

## Search

- Используй только MCP `user-tasks-qdrant`.
- В реестре инструментов дефисы имени сервера нормализуются в подчёркивания: native tools имеют префикс `mcp__user_tasks_qdrant__`. Если tools не видны, выполняй discovery по `user_tasks_qdrant` или этому полному префиксу; поиск только по `user-tasks-qdrant` не доказывает недоступность сервера.
- Вызови `search_observations(project, query, k=60)` и `search_tasks(project, query, k=30)`; независимые search calls можно выполнить в одном tool round.
- Preview уже отсортирован сервером по `final_score` с учётом freshness от `score_tick`.
- Не вычисляй score/freshness, не делай embeddings и не используй REST, shell, scroll или list fallback.
- Если после discovery native tools не найдены или MCP call упал, скажи `taskdb read недоступен` и продолжай без taskdb context.

## Select And Load

- Сначала ищи точные query terms в `summary` и `tags`. Высокий `final_score` не делает соседний class, file, endpoint или похожую error релевантными точному запросу.
- Если точных записей нет, используй только действительно применимый общий architecture pattern, registration method, folder structure, workflow или известную ловушку.
- Не добирай записи до лимита. Допустимо не загружать ни одного body.
- Для применимых preview вызывай `get_observation` / `get_task`. Обычно достаточно 3–8 observations и 1–3 tasks; максимум — 10 observations и 5 tasks.
- Загружай body, только если он может изменить решение, содержит прошлый bug/pattern, даёт места для проверки или summary выглядит конфликтным либо устаревшим.

## Use

- В рабочем context сохраняй только выводы: facts, constraints, risks, patterns и места для последующего чтения кода.
- В `used_records` держи только `{kind,id}` загруженных записей, которые реально повлияли на работу.
- Устаревшие или противоречивые записи держи отдельно как `stale_records` для возможной write-ветки; не отмечай их used.
- После lookup сверяй выводы с кодом. При конфликте код — источник истины.
- Не показывай пользователю ids, scores, tags, raw JSON и body quotes. Пути из taskdb не раскрывай как сырую метаинформацию; подтверждённые по коду пути можно использовать обычно.
- Если найден применимый context, скажи `Нашёл похожее в taskdb.`; если релевантного нет, продолжай без отдельного сообщения.

## Read-only Boundary

- Не вызывай `add_*`, `update_*`, `delete_*`, `mark_*_used` и `migrate_*`.

## Completion

- Lookup завершён, когда search calls обработаны, загружены все и только нужные body в пределах лимита, сформированы выводы и `used_records` / `stale_records` либо зафиксирован исход empty, unavailable или unclear project. Только после этого продолжай автоматическую ветку с кодом.
