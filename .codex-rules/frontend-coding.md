# Frontend Coding

Общие правила компонентов, состояния, UI-проверки и тестовых сценариев для Angular, React и Flutter; фреймворк-специфичные файлы дополняют их.

## Components And State

- Компонент или widget отвечает за UI, user interaction, локальное UI state и orchestration.
- Выноси бизнес-правила, data access и integration-код, когда они повторяются, имеют самостоятельный доменный смысл или мешают читать UI.
- Не делай огромный компонент, но и не дроби UI механически. Локальный one-use fragment держи рядом; общий UI выноси после второго использования или при явном design contract.
- Держи state у ближайшего владельца. Поднимай его или переноси в проектный state manager только при реальной общей потребности.
- Для async UI явно учитывай применимые состояния: loading, data, empty и error.

## TypeScript

- В TypeScript используй arrow functions для callbacks и handlers, если они читаются проще.
- Явно типизируй props, inputs, outputs, публичные методы, service API и нетривиальные async results.
- Не оставляй `any`: внешние данные сужай или валидируй на границе.
- Разделяй DTO, domain model и view model, когда формы данных различаются.

## Visual Check

- Перед браузерной проверкой frontend прочитай `.codex-rules/playwright-testing.md` и следуй описанному там процессу живой UI-приёмки.
- После изменения UI или frontend-поведения визуально проверь изменённый экран, если приложение уже запущено или пользователь прямо разрешил запуск.
- Для web UI используй режим, выбранный по `.codex-rules/playwright-testing.md`. Браузерная проверка не заменяет widget/integration-подход для нативного Flutter.
- Проверь относящиеся к задаче состояния и действия: видимость, клики, hover, ввод, keyboard navigation, нужные viewport и сетевой контекст.
- Если приложение не запущено, не запускай dev server или native app без прямой просьбы. В финальном ответе явно укажи, что визуальная проверка не выполнена и почему.

## UI Scenarios

- Проверяй user-visible behavior и результат, а не внутренний flow, private hooks или CSS-классы без продуктового смысла.
- Перед исправлением нестабильного UI-поведения сначала воспроизведи сценарий: открой экран, выставь viewport, выполни действия и проверь видимый результат.

## Completion

- UI-задача завершена, когда каждое изменённое поведение проверено релевантным видимым сценарием либо явно зафиксирована конкретная причина, почему визуальная проверка недоступна.
