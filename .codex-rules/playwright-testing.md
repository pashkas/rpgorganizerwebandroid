# Playwright Testing

Правила исследовательской и повторяемой проверки web UI через изолированный headless Playwright. Постоянные UI-тесты и test runner в проекте не создавай.

## Выбрать режим

До первого действия проверь полномочия на запуск приложения, доступные данные и возможные внешние изменения. По умолчанию проверка read-only: не отправляй формы и не запускай изменяющие операции без прямого разрешения.

- Используй Playwright MCP, пока экран, данные, locator или следующий шаг неизвестны. MCP предназначен для разведки, диагностики и короткого адаптивного сценария.
- Переноси сценарий в глобальный Playwright CLI, когда шаги и проверки уже известны и тот же маршрут предстоит выполнить минимум два раза, в том числе после исправлений.
- Не запускай известную длинную последовательность повторными MCP-вызовами, если её можно проверить одним временным CLI-сценарием с компактным PASS/FAIL.
- MCP и CLI работают в отдельных изолированных headless-сессиях. Не пытайся разделить между ними активную браузерную сессию.
- Если обязательная авторизация или состояние недоступны в изолированном Playwright, верни `BLOCKED` и укажи условие разблокировки.
- Не используй `browser_run_code_unsafe` и CLI `run-code`. Пакетную логику держи в проверяемом временном PowerShell-файле.

## Выбрать URL

- Если пользователь дал URL, используй его без замены порта или контура.
- Для op26 интегрированный frontend обычно доступен на `http://localhost:8801`, CRA dev-server — на `http://localhost:3000`.
- Если URL не задан, выбери уже запущенный контур, соответствующий задаче. Не запускай приложение без прямого разрешения.

## Исследовать через MCP

- После навигации сначала используй `find` или snapshot небольшой глубины.
- Для таблицы сначала получи refs строк коротким snapshot, затем запроси только нужную строку. Не раскрывай весь `rowgroup`, если нужна одна запись.
- После изменения состояния используй новый ref из актуального snapshot или `find`; refs относятся только к текущей сессии.
- Console и network запрашивай с минимальным уровнем и фильтром по относящемуся endpoint.
- Screenshot делай только для визуального требования; для действий используй accessibility snapshot.
- Закрывай MCP-сессию после разведки или перед независимым CLI-прогоном.

## Подготовить Playwright CLI

В начале временного сценария получи абсолютные пути:

```powershell
$playwrightNode = Join-Path $env:APPDATA 'nvm\v20.19.4\node.exe'
$playwrightCli = Join-Path $env:APPDATA 'npm\node_modules\@playwright\cli\playwright-cli.js'
```

- Не выполняй `nvm use`, не меняй активную версию Node.js и не вызывай npm/npx.
- Проверь `& $playwrightNode $playwrightCli --version`. Если Node.js или глобальный CLI отсутствует, не устанавливай их в рамках UI-проверки; продолжай через MCP либо верни `BLOCKED`, если повторяемый прогон обязателен.
- Вызывай CLI напрямую: `& $playwrightNode $playwrightCli "-s=$session" <command>`. После каждого вызова проверяй `$LASTEXITCODE`.
- Дай сессии уникальное имя по задаче. Не используй `close-all` и `kill-all`; в `finally` закрывай только свою сессию командой `close`.
- Запускай сценарий через `pwsh -NoProfile -NonInteractive -WindowStyle Hidden -File <script-path>`.
- CLI daemon пишет в пользовательский каталог Playwright. Если sandbox блокирует этот доступ, запроси разрешение на запуск конкретного временного сценария.

## Подготовить временный сценарий

Создавай временный `.ps1` в `.tmp-scripts/playwright/<task-id>`. Не добавляй UI-тесты, Playwright-зависимости, config, npm-скрипты и bat-файлы в frontend или другой проектный модуль.

- Переноси в сценарий только уже проверенные MCP шаги и ожидаемые видимые результаты.
- Предпочитай роли, labels, осмысленный текст и устойчивые признаки данных. Позиционный или структурный selector допустим во временном сценарии, когда он прямо выражает проверяемое действие, например выбор первой строки.
- Используй ожидания самого Playwright; не добавляй фиксированный sleep.
- Каждый обязательный результат проверяй явно. При дефекте сценарий должен завершаться ненулевым exit code.
- Перехватывай или отменяй изменяющий запрос, пока пользователь не разрешил реальную отправку.
- Выводи только компактные строки `PASS`, а при ошибке — проверяемое условие и нужный диагностический контекст. Не печатай полный snapshot, console или список запросов при успешном прогоне.
- Не сохраняй пароль, token, cookie, environment secret и `storageState`.

## Выполнить и повторить проверку

После MCP-воспроизведения дефекта создай временный CLI-сценарий до исправления, если это безопасно и сценарий предстоит повторять. По возможности подтверди, что он падает на исходном поведении.

- После каждой правки запускай тот же файл. Меняй сценарий только при изменении требования или при доказанной ошибке самого сценария.
- Не запускай весь project suite: UI-проверка выполняется только конкретным временным файлом.
- Для визуального требования временно сохрани screenshot; для сложного падения — относящиеся к нему snapshot, console или requests.
- В итоговом сообщении укажи проверенные состояния, команду запуска, результат и ограничения. Не выдавай ручное описание кликов за воспроизводимое доказательство, если CLI-сценарий был доступен.
- После завершения задачи закрой свою сессию и удали созданные сценарии, snapshot, screenshot, trace, отчёты и пустые временные каталоги. Не удаляй артефакты других задач.

Проверка завершена, когда каждое изменённое UI-поведение подтверждено MCP-разведкой либо воспроизводимым CLI-сценарием, а все созданные временные файлы удалены.
