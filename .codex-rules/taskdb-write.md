# Taskdb Write

Записывай в taskdb только явно разрешённый законченный результат, переиспользуемые факты и подтверждённое использование прошлых записей; само чтение этого файла не даёт разрешения на write.

## Decide

- Условие запуска бери из project router или прямой просьбы пользователя.
- При каждой команде записи собери все подходящие результаты и наблюдения текущей сессии, которые ещё не были успешно записаны в taskdb.
- Создавай `task` для законченного результата, подтверждённого изменёнными или проверенными файлами: fix, feature, refactoring, bug diagnosis с выводом, pipeline setup, обновление rules или infrastructure.
- Каждый независимый законченный результат записывай отдельным `task`; не объединяй несвязанные задачи сессии в одну запись.
- Не создавай `task` для обычного ответа, пересказа кода, непроверенного совета, расследования без результата или результата без конкретного `affected`.
- Создавай `observation` для переиспользуемого факта о проекте: hidden invariant, nonstandard config, historical decision, user rule, risk, trap, exact data path, important command или constraint.
- Один независимый факт записывай одним `observation`. Не записывай очевидное из имени файла или одной строки кода.
- После успешного `add_task` или `add_observation` считай соответствующий элемент записанным до конца текущей сессии. При следующей команде записывай только новые и ранее не записанные элементы.
- Если отдельный `add_*` завершился ошибкой, не считай элемент записанным и повтори попытку при следующей команде записи.
- Не выполняй dedup search перед записью.
- Сохраняй полученные при read `used_records` и `stale_records` раздельно.
- Если нет новых records, used records и stale records, скажи `В taskdb писать нечего.` и остановись до tool discovery.

## Project And Tools

- Имя проекта бери из текущего запроса или уже загруженного project context.
- Если имени нет или есть конфликт, скажи `taskdb не инициализирован, используй user-tasks-qdrant-init` и остановись.
- Используй native MCP tools сервера `user-tasks-qdrant`: `add_task`, `add_observation`, `mark_task_used`, `mark_observation_used`, `get_*`, `update_*` и `delete_*`.
- В реестре инструментов дефисы имени сервера нормализуются в подчёркивания: native tools имеют префикс `mcp__user_tasks_qdrant__`. Если tools не видны, выполняй discovery по `user_tasks_qdrant` или этому полному префиксу; поиск только по `user-tasks-qdrant` не доказывает недоступность сервера. Не используй Qdrant REST, shell или HTTP fallback.
- Если tools остались недоступны, скажи `MCP user-tasks-qdrant недоступен, taskdb не обновлён.` и остановись.

## Task Format

- `summary`: одно предложение, сформулированное как будущий search query о симптоме, месте и context; не пиши `Исправили...`, `Сделали...` или `Агент...`.
- `body`: Markdown с обязательными `## Условие` и `## Что сделали`; добавляй `## Причина`, только если decision или tradeoff полезен в будущем.
- В `## Условие` укажи исходную задачу, symptom, context и важные constraints. В `## Что сделали` — фактический result и изменённые contracts.
- Не добавляй `## Затронуто` / `## Где в коде`: для этого есть `affected`.
- `affected`: минимум один конкретный `{path, symbol?, line?}`.
- `tags`: 3–8 concrete tags плюс `created:YYYY-MM-DD`.
- Язык записи — язык пользователя.

```text
add_task(
  project=<project>,
  summary="Короткий поисковый симптом или контекст",
  body="## Условие\n...\n\n## Что сделали\n...\n\n## Причина\n...",
  tags=["подсистема", "файл", "термин", "created:YYYY-MM-DD"],
  affected=[{"path":"path/to/file.ext","symbol":"ClassOrFunction"}]
)
```

## Observation Format

- `summary`: один стабильный факт, пригодный для поиска по symptom, domain или term.
- `body`: 3–8 строк о факте, его месте, важности и ошибке при игнорировании.
- `affected`: обычно 1–2 concrete `{path, symbol?, line?}`; без `affected` observation не записывай.
- `tags`: 3–6 concrete tags плюс `created:YYYY-MM-DD`.
- Не превращай observation в отчёт о выполненной задаче.

```text
add_observation(
  project=<project>,
  summary="Стабильный факт о проекте",
  body="Факт: ...\nГде: ...\nПочему важно: ...",
  tags=["подсистема", "термин", "created:YYYY-MM-DD"],
  affected=[{"path":"path/to/file.ext","symbol":"ClassOrFunction"}]
)
```

## Used And Stale Records

- Отмечай `mark_*_used` только для актуальных `used_records`, которые повлияли на решение, дали context, constraint, term, risk или direction.
- Не отмечай запись used только за попадание в search results.
- Не ищи stale специально. Обрабатывай только `stale_records`, всплывшие в текущей сессии или явно названные пользователем.
- Перед изменением stale record прочитай его через `get_*`.
- Используй `update_*`, если запись остаётся тем же фактом или task и нужно исправить поля. Если содержание устарело, сначала добавь актуальную запись.
- Удаляй заменённую stale record только если её `created:*`, `migrated:*` или `updated:*` старше 7 полных дней. Более молодую оставь рядом с актуальной.
- Если правильность удаления неочевидна, оставь старую запись.

## Encoding

- Передавай русский text в native MCP обычной Unicode string без ручного перекодирования.
- Исправляй `????` через `update_*` только после подтверждения, что испорчено сохранённое поле. Mojibake `Ð...` только в PowerShell output не доказывает порчу данных.

## Order And Report

1. Добавь все новые observations.
2. Добавь все новые tasks.
3. Отметь актуальные used records.
4. Последними обнови или очисти stale records.

- Сообщай `Записал в taskdb.`, только если все обязательные calls завершились успешно.
- Если часть calls упала, сообщи `Taskdb обновлён частично: <кратко что не выполнено>.` без ids и bodies.
- Если stale records заменены или исправлены, а остальные calls успешны, сообщи `Обновил taskdb: записал актуальное и обработал протухшее.`
- Не показывай пользователю ids, bodies и raw tool output.

## Completion

- Write завершён, когда каждый ещё не записанный подходящий независимый факт учтён один раз, для каждого ещё не записанного законченного результата создан отдельный task, актуальные used records отмечены, stale branch обработана безопасно и финальный отчёт точно отражает исход всех calls.
