# Coding Rules

Общие правила для создания, изменения, рефакторинга и ревью кода независимо от языка и фреймворка.

## Structure

- Пиши максимально простой, последовательный и читаемый код без скрытого замысла: главный сценарий держи линейным, имена выбирай по доменному смыслу.
- Решай текущую задачу самым простым способом, который сохраняет понятные границы сценария, I/O, конфигурации, валидации и форматирования. Не добавляй классы, интерфейсы, дженерики, конфигурацию или гибкость «на будущее».
- Используй привычные проекту возможности языка, если они сокращают шум и яснее выражают намерение. Не применяй сложную или редкую конструкцию только ради краткости или демонстрации возможностей языка.
- Не превращай `main()`, handler, service method или компонент в монолит.
- Если функция или метод не однострочный и перед итоговым `return` есть подготовка, оставляй перед `return` пустую строку.

## Abstractions And Flow

- Добавляй абстракцию только когда она выражает доменный смысл, убирает реальный дубль или заметно снижает сложность.
- Не добавляй helper, wrapper, interface, class, service или extension только ради структуры.
- Однократно используемый фрагмент по умолчанию оставляй inline. Не выноси его в helper только ради единого уровня абстракции. Сохраняй helper, если его имя выражает самостоятельное доменное действие, он скрывает шумный низкоуровневый код, защищает порядок side effects или заметно облегчает чтение основного сценария.
- Выноси метод, когда логика повторяется, имеет самостоятельный смысл или существенно разгружает вызывающий сценарий. Не дроби код на мелкие методы без выигрыша.
- Не устраняй механически любое повторение. Выноси общий код, когда это одно поведение, которое должно изменяться согласованно, а имя общей части выражает понятный смысл; небольшой очевидный повтор допустим, если абстракция усложнит чтение.
- Объединяй дублированные ветки только при одинаковом поведении.
- Используй guard clauses и ранние выходы, когда они уменьшают вложенность и делают основной сценарий линейнее. Не вводи искусственные флаги, дополнительные методы или инвертированные условия только ради устранения вложенности или `else`; оставляй `else`, когда он ясно показывает взаимоисключающие симметричные ветки.
- Сложное условие называй доменной переменной. Промежуточную переменную добавляй или убирай только ради ясности.
- Выбирай цикл или functional chain по читаемости; не уплотняй понятный сценарий.
- Явные крайние случаи обрабатывай рядом с местом, где они важны. Fallback и защиту добавляй только для реальных сценариев.

## Contracts And Errors

- Не меняй public API, DTO/JSON/XML/XSD contracts, SQL/Mongo criteria, transaction boundaries, security logic и порядок side effects без явной задачи.
- Не оставляй `public` по инерции: сужай видимость или делай inline, если это не API, override, framework contract или внешний контракт.
- Перед удалением private/internal кода точечно найди его использования.
- Не глотай исключения и не используй bare `catch` / `except`.
- Оставляй `try/catch` только для восстановления, доменного преобразования ошибки, компенсации состояния или полезного лога с контекстом.
- Не оборачивай исключение без нового смысла. Лог должен добавлять контекст, а не повторять stack trace.

## Comments And Data

- Комментарии к коду, логи и консольный вывод пиши по-русски, если проект не требует другого языка.
- Структура, имена и поток выполнения должны объяснять, что делает код, без поясняющих комментариев. Комментируй намерение, доменное правило, причину решения или неочевидный риск — то, чего сам код выразить не может.
- Для метода или функции кратко пиши, что она делает; параметры и return не пересказывай без необходимости.
- Для путей используй стандартный path API языка, для JSON и DTO — структурные модели или явные parse/serialize-функции.
- Не размазывай сырой `dict` / `map` / JSON по проекту.
- Текстовые файлы читай и пиши явно в UTF-8.
- Не хардкодь пути к пользователю, машине, книге, модели или локальной среде.
- Временные скрипты держи в указанной проектом temp-папке; если правила проекта её не задают, используй отдельную папку внутри проекта. После использования удаляй скрипты.

## Performance

- Исправляй очевидную неэффективность: повторные вычисления, лишние проходы, дорогие операции в цикле и ненужные объекты.
- Не меняй читаемость на микрооптимизацию.
- Большие файлы, книги, JSON и аудио обрабатывай потоково или частями, когда полный объём действительно создаёт проблему.

## Completion

- Перед завершением классифицируй каждый добавленный или изменённый helper-like метод: inline, private, внешний контракт или удалить.
- Убедись, что изменённый сценарий остаётся линейным, публичные контракты и порядок side effects сохранены, а каждая оставшаяся абстракция снижает сложность или выражает доменный смысл.
